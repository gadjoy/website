# Implementation Plan: Progressive Web App

**Spec**: [spec.md](spec.md) | **Date**: 2026-10-10

## Order

Icons first, because they are the only part that cannot be hand-written and because
installability is gated on them. Then the manifest (static, inspectable). Then the service
worker, which is the only part with real failure modes. Tests precede each (Principle I).

## Phase A — Icons

`static/img/logo.png` is 512×497 RGBA — nearly square but not square, and Chrome refuses
installability on non-square icons. Pad to a square canvas on the existing background
colour; do not stretch, which distorts the mark.

A **maskable** icon is a separate file, not the same image relabelled: Android crops to a
circle and clips ~10% on each edge, so the mark needs its own padding. Relabelling the
standard icon as maskable is the common mistake and produces a logo with its edges sliced
off.

Generated by a committed script so the derivation is reproducible, with the output
committed too — the build must not depend on Pillow being present.

## Phase B — Manifest

A Hugo template reading `hugo.yaml`, not a static file: Principle X requires public-facing
values to trace to a source. Hugo outputs it via a custom output format so the path is
stable and the content type is right.

## Phase C — Service worker

The part that can actually break the site, so the design is deliberately small.

**Three caches, versioned together:** shell, pages, assets. `activate` deletes anything
whose version prefix differs. A service worker that cannot be retired is the classic
failure here — the user gets a stale site and clearing it needs devtools.

**Routing:**
- POST and cross-origin → straight to the network, untouched. FR-008 is the important one:
  a queued enquiry the customer believes was sent is worse than a visible failure.
- HTML → network-first, falling back to cache, falling back to the offline page. Network
  first because a published repair post must never be served stale.
- Images/CSS/fonts → cache-first, because they are effectively immutable here.

**Registration** goes in the existing `custom_headers.html` partial, guarded on
`navigator.serviceWorker`, after load so it never competes with first paint. It must not
change rendering (FR-010) — the visual baselines are the check.

## Risks

- **A bad service worker is sticky.** It outlives a deploy and can serve a broken site to
  returning visitors. Mitigated by versioned caches, `skipWaiting`/`clients.claim`, and by
  testing the upgrade path rather than only the install path.
- **Screenshot nondeterminism.** A service worker caching between captures could make the
  visual gate flap. The e2e contexts are fresh per test, so it should not arise — but
  SC-011 exists to catch it rather than assume.
- **Offline tests are easy to write vacuously.** "Set offline, assert something rendered"
  passes when the browser serves its own error page. The assertions name Gadjoy content
  specifically.
