# Feature Specification: Progressive Web App

**Branch**: `feat/pwa` | **Date**: 2026-10-10 | **Constitution**: v2.0.0

## Problem

A customer standing outside the shop with no signal cannot see the address, the hours or the
phone number. That is the actual gap worth closing, and it is the one a PWA closes cheaply.

The installable-app part is the less valuable half, and this spec says so rather than
overselling it: people visit a repair shop's site once or twice, not daily. The durable win
is **offline access to how to reach the shop**, plus faster repeat loads.

### What this cannot do, stated up front

**Push notifications for "your repair is ready" are out of scope and not merely deferred.**
They need a backend to send them, and this site has none — the contact form posts to
Web3Forms and nothing else exists server-side. Recording that here so the next person does
not read "PWA" and assume push came with it.

**The whole site cannot be cached.** The build is 198 MB across 3,630 pages. Anything
claiming "the site works offline" would be false. What works offline is a named, small set
of pages and whatever the visitor has already seen.

## User Scenarios

### US1 — The shop's details work with no signal (P1)
A customer loses signal outside the shop. The address, phone number, WhatsApp link and
opening hours are still on screen.

### US2 — A page already visited opens offline (P1)
A repair post read on the bus opens again in a tunnel.

### US3 — An unvisited page fails honestly (P1)
A page never fetched, with no network, shows a Gadjoy offline page saying so — not a browser
error, and not a blank screen that looks like the site is broken.

### US4 — The site is installable (P2)
Chrome and Android offer "Install"; iOS offers "Add to Home Screen" and the result opens
without browser chrome.

## Requirements

### Manifest
- **FR-001** — A web app manifest is served at a stable path, generated by Hugo from
  `hugo.yaml` so the name, colours and description trace to a source (Principle X), never a
  template literal.
- **FR-002** — Icons at **192×192 and 512×512, square**, plus a **maskable** variant.
  Generated from the existing brand logo by padding to a square canvas — not redrawn, and
  not stretched, which would distort the mark.
- **FR-003** — `display: standalone`, `start_url: /`, and a `theme_color`/`background_color`
  matching the site's existing palette rather than invented.

### Service worker
- **FR-004** — Registered at **root scope** from `/sw.js`. GitHub Pages cannot set
  `Service-Worker-Allowed`, so scope widening is impossible; serving from root avoids ever
  needing it.
- **FR-005** — Precaches a small **app shell** only: the offline page, the contact page, the
  icons and the stylesheet. Never the 3,630-page corpus.
- **FR-006** — **Network-first for HTML**, so a published repair post is never served stale
  from cache. Cache-first for immutable assets (images, CSS, fonts).
- **FR-007** — An **offline fallback page** carrying the shop's address, phone, WhatsApp and
  hours — the US1 payload — served when an HTML request fails and nothing is cached.
- **FR-008** — **Never intercepts the enquiry form's POST.** A queued or replayed enquiry
  would be worse than a failed one: the customer believes it was sent.
- **FR-009** — Caches are **versioned**, and activation deletes caches from older versions.
  A stale service worker serving a previous build is the classic failure of this pattern.
- **FR-010** — Registration must not alter rendering. The existing visual baselines must
  continue to pass unchanged.

### Honesty
- **FR-011** — Nothing in the UI claims the whole site works offline.

## Out of Scope

- **Push notifications** — no backend exists to send them (see above).
- **Background sync** of enquiries — same reason, and FR-008 is the deliberate opposite.
- Caching the full post corpus.
- An in-page "Install" button. The browser's own prompt is enough, and a custom button is
  another contact-affordance-style duplication waiting to happen (see Phase 3 of the
  working plan).

## Constraints

- **GitHub Pages sets no response headers**, so `Service-Worker-Allowed` is unavailable.
  FR-004 is written to not need it.
- The site is served from an **apex custom domain** (`gadjoy.in`), so root scope is
  available. On a project subpath it would not be.
- The build is **198 MB / 3,630 pages**; precaching is necessarily selective (FR-005).
